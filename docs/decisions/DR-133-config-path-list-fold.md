# DR-133: config パス列の fold — スコープの全 config_file が供給するパスを宣言順に読み、トップキー置換で 1 オブジェクトへ畳む

> 由来: kawaz 裁定 CFM-Q1a (2026-08-12) と、その下位軸 CFM-Q2 の裁定 (2026-08-12、mid=1-5)。
> **DR-050 の射程外項「複数の config_file 要素の合成 (システム設定 + ユーザ設定の 2 要素等) は本 DR では
> 確定しない。canonical は単一の config_file 要素」を確定させる。** 前提は DR-050 (config ファイル値源の
> 正本) / DR-031 (値源ラダーの config 席) / DR-037 (Reject と Error の分界)。

## 決定

### 1. 席埋め規則は 1 本 — 単体と複数を分けない

config 席 (DR-031 #3) を埋めるオブジェクトは、次の 1 つの規則で決まる。**パス列から 1 個のオブジェクトが
出る**、それだけである:

1. **パス列を作る** — そのスコープの config_file 要素を**宣言順**に走査し、各要素が供給するパスを列の
   末尾に足す
2. **各パスを順に読む** — 列の各パスを provider へ渡す。provider 契約は不変 (`(path: string) → 階層
   オブジェクト | null`、DR-050 §2)。列の長さだけ呼ぶ
3. **トップレベルキー置換で畳む** — 読めたオブジェクトを列の順に畳む。後のオブジェクトが持つ
   **トップレベルキー**が前のものを置き換え、後のオブジェクトに無いトップキーは前の値がそのまま残る

**単体の config_file 要素はパス列長 1 の縮退形**であり、従来の挙動と一致する。単体と複数で別の規則を
持たない。

#### 1.1 パス列への参加

- **パスを供給しなかった要素は列に参加しないだけ** — config_file 要素のパスは要素ごとに独立な
  cli > env > default のラダーで解決される (DR-050 §1)。どの席からも供給されなければ読むべきファイルを
  指していないので、列に足すものが無い。エラーではない
- **`multiple` の config_file 要素は自分の位置に供給順で inline 展開する** — 1 要素が複数パスを供給する
  ときは、その要素が宣言順で占める位置に、供給順のパスがそのまま並ぶ。要素の綴り (単体を複数個 /
  multiple を 1 個) で fold の意味が変わることはない

```json
{"options": [
  {"name": "sys",  "type": "config_file", "long": true, "default": "/etc/app.toml"},
  {"name": "user", "type": "config_file", "long": true, "multiple": true},
  {"name": "site", "type": "config_file", "long": true, "default": "/site.toml"}
]}
```

`--user /u1.toml --user /u2.toml` なら、パス列は `/etc/app.toml, /u1.toml, /u2.toml, /site.toml` になる。

### 2. 畳むのはトップレベルキーまで — 深いマージはしない

fold はトップレベルのキー単位でのみ置換する。ネストした object の内側を再帰的に混ぜることはしない
(後のファイルのトップキーが object なら、その object 丸ごとで前を置き換える)。

**v1 にダイヤル語彙を持たない** (CFM-Q2-γ)。深いマージの需要は、合成済みのオブジェクトを返す
config_provider か、将来の別語彙が担う。深いマージを core に入れると「配列は連結か置換か」「欠損キーの
扱い」といったダイヤルを必ず呼び込み、語彙が増え続ける。

fold は値の中身を検査しない — キーに対応する値をそのまま置くだけである。JSON `null` の読み
(「供給なし」、DR-050 §4) は畳んだ後のオブジェクトを席が読む段の規則であって、fold の関心ではない。

### 3. committed Error と default 由来不在の黙認は、各パス独立に判定する

DR-050 §2 の分界は列の各パスにそれぞれ適用される (CFM-Q2-α):

- **committed なパス (cli / env 明示) の読込失敗は Error** — 指定したのに読めないので、そのパスを
  供給した要素に帰属する Error になる
- **default 由来のパスの不在は黙認** — 設定ファイルはオプショナルという慣習どおり、そのパスは fold に
  寄与しないだけで列の残りは読まれ続ける

前のパスの committed 性が後のパスの判定に影響することはない。判定はパスごとに閉じている。

### 4. 複数要素を書くことが「重ねる」の宣言である

複数の config_file 要素 (または multiple の複数パス) を書いた定義は、**重ねを宣言している**。system 設定 +
user 設定のように、下地を後段が部分的に上書きする形がそのまま書ける。

**排他的なファイル選択**をしたい定義は **1 つの要素**で書く — 要素内の値源ラダー (cli > env > default) が
既に「どれか 1 つを選ぶ」を担っており、選ばれた 1 本だけが列に入る。「どれか 1 つ」と「重ねる」は
要素の数で書き分ける。

### 5. 射程は同一スコープ内

本 DR が規定するのは、**同じスコープに宣言された** config_file 要素どうしの関係である。異なるスコープ
(root と子 command 等) に宣言された config_file の関係は確定しない (「射程外」節)。

### 6. DR-050 §2 の分界の読み直し

DR-050 §2 の「複数ファイルのマージ戦略は provider の関心」は、**1 つのパス指定から provider が探索して
合成する類**を指す (CFM-Q2-β)。定義が**宣言した複数パス**の fold は core の席埋め規則であり、本 DR が
正本である。両者は競合しない — provider は 1 パスから 1 オブジェクトを返す契約のままで、その先の
重ねを core が持つ。

## 根拠

### 分ける理由が無い

「パス列 → 1 オブジェクト」の 1 規則で、単体・複数要素・multiple のすべてが説明できる。要素の数や
綴りで意味論を分岐させると、利用者は「どちらの書き方をしたか」で結果が変わることを覚える羽目になる。
分岐を作らないほうが規則も実装も小さい。

### 重ねは複数宣言の動機そのもの

複数の config_file 要素を書きたい動機は system + user のような**下地と上書き**であり、shell rc / git config
など既存の設定系の慣習もキー単位の重ねである。重ねられない規則にすると、複数宣言の用途が「排他選択」
だけに縮み、そちらは 1 要素の値源ラダーで既に書ける — つまり複数宣言を認める意味がほとんど無くなる。

### provider 契約は無傷

fold は provider を N 回呼ぶだけで、1 パス → 1 オブジェクトの契約 (DR-050 §2) には触れていない。core が
持つのは「宣言された順に畳む」という**宣言の読み方**であって、ファイルの探索や合成の知識ではない。

必要がある。committed 性を要素間で持ち越す不具合 (§3 に反する) も同じ箇所にある。

## 採用しなかった案

### オブジェクト全体置換 — 最後にパスを持つ要素だけを読む (CFM-Q2 の (a)、旧 DR-133 の形)

勝った 1 パスだけを provider へ渡し、負けたパスは読まない形。参照実装の現挙動でもある。**複数宣言の
動機である重ねが実現できない** — 後段のファイルに無いキーが前段から採られないので、system + user の
下地関係が書けない。加えて負けたパスを読まないため、committed 指定したのに読まれないパスが生まれ、
「指定したのに読めないのは失敗」(DR-050 §2) の判定から静かに外れる。

### 単体要素間は全体置換、`multiple` の要素内だけ fold (CFM-Q2 の案 c)

同じ「複数のパス」が、単体要素を並べたか multiple を使ったかで別の意味になる。利用者から見て綴りの
違いが意味論の違いになるのは覚える負荷が高く、fold を 1 本に統一すれば消える分岐である。

### 先勝ち (CFM-Q1b)

先に宣言した要素が勝つ形。上書きの向きが設定レイヤの慣習と逆になる。fold の下では「先に書いたものが
下地」という自然な読みがそのまま成り立つ。

### 複数指定を definition-error にする (CFM-Q1c)

由来の違う設定ファイルを別々の入口 (long / env / default) で受け取る需要を定義側から締め出す。

### 深いマージ意味論 (CFM-Q1d)

§2 のとおりダイヤルを呼び込む。トップキー置換で止めるのは、規則を 1 文で言い切れる水準に保つため。

## 射程外

- **異なるスコープに宣言された config_file の関係** — root の config_file が子スコープの要素へ供給するか、
  子スコープ側の宣言が root を上書きするか。DR-050 §3 の同型対応 (`serve.port` ↔ config の `serve.port`) は
  root 宣言の config が木全体へ効く像を前提にしているが、参照実装はスコープごとに独立に解決しており
  root の config_file が子スコープの要素へ供給しない (実測 2026-08-12)。spec と参照実装の食い違いの解消を
  含めて別途扱う (`docs/issue/2026-08-12-nested-config-not-supplied.md`)
- config ファイルの watch / 実行時再読込、プロファイル切替 (DR-050 の射程外のまま)
- 深いマージのダイヤル語彙 (§2)
