# DR-133: config パス列の fold — 1 スコープ 1 config_file、その要素が供給するパス列をトップキー置換で畳む

> 由来: kawaz 裁定 CFM-Q1a / CFM-Q2 (2026-08-12) を **CFM-Q3a (2026-08-14) で再改稿**。初版は
> 「そのスコープの全 config_file 要素を宣言順に走査してパス列を作る」という**要素間規則**を持っていたが、
> これは mid=8 の誤読だった — fold は **1 つの config_file 要素が multiple で供給するパス列**に定義する
> ものであり、複数要素の並置には意味が無い。CFL-Q1a (2026-08-14) の committed 判定の link 透過も
> 本 DR が受ける。前提は DR-050 (config ファイル値源の正本) / DR-031 (値源ラダーの config 席) /
> DR-037 (Reject と Error の分界) / DR-135 (config_file は通常要素)。

## 決定

### 1. 1 スコープ 1 config_file — 並置は definition-error

**同一スコープに 2 つ以上の `type: "config_file"` 要素を宣言することはできない。** 置いた場合は
definition-error **kind = `invalid-range`**、`element` は**並置に関与した config_file 要素ごとに 1 件**を
全列挙する (DR-054 §4 の全列挙原則。代表 1 件にすると相方が expect から読めない — DR-120 §5 と同じ理由)。

理由は席の数である。**config 席はスコープに 1 つ**であり (DR-031 #3)、それを埋めるオブジェクトも 1 つ
(§2)。2 つ以上の config_file 要素は同じ 1 席への重複宣言であって、席の値域外にある。

kind に `invalid-range` を採るのは、**同居不可の組合せ**を表す既存 kind だからである (DR-134 §2 が
値持ち command と占有子の共存に採ったのと同じ筋。`default` と `default_fn` の併用、非 multiple 要素への
`accum_filters` など、同居できない構成は一貫してこの kind で報告されている)。新 kind を興さないのは、
`export-key-collision` のように**固有の解決手段の出し分け** (DR-120 §5 の hint) を持つ性質が無く、
「その構成は書けない」以上の情報を運ばないためである。

### 1.1 重ねの正規形は 1 要素の `multiple`

system 設定 + user 設定のような**重ね**は、1 つの要素が複数パスを供給する形で書く:

```json
{"name": "config", "type": "config_file", "multiple": "append", "long": true,
 "env": "MYAPP_CONFIG", "default": ["/etc/app.toml", "~/.app.toml"]}
```

並置で書きたくなる動機は、すべて 1 要素に収まる:

- **綴り違いの入口** (`--config` / `--config-file`) — `alias` (DR-057) が 1 セルに複数綴りを与える
- **由来の違う入口** (CLI / env / 既定) — 1 要素の値源ラダーが元から 3 席を持つ (DR-050 §1)
- **既定のパス列** — 配列 `default` で書く (上例)
- **分割して指定したい** — `default_fn: "borrow:<外側要素名>"` (DR-125 §3) で 1 要素に集約する

### 1.2 「探す場所が複数」は重ねではない

「複数の候補パスを探して**最初に読めた 1 個**を使う」は探索であって重ねではなく、本 DR の対象外。
file 要素 + readable filter (I/O 述語の新カテゴリ) + borrow の**合成**で書く方向で、語彙の席は別途扱う
(`docs/issue/2026-08-12-io-predicate-vocabulary-seat.md`)。fold にダイヤルを足して探索を兼ねさせない。

### 2. 席埋め規則 — パス列から 1 オブジェクト

config 席 (DR-031 #3) を埋めるオブジェクトは、次の 1 つの規則で決まる。**パス列から 1 個のオブジェクトが
出る**、それだけである:

1. **パス列を作る** — そのスコープの config_file 要素が供給するパスを**供給順**に並べる
   (`multiple` の供給順は DR-034 / DR-105)
2. **各パスを順に読む** — 列の各パスを provider へ渡す。provider 契約は不変 (`(path: string) → 階層
   オブジェクト | null`、DR-050 §2)。列の長さだけ呼ぶ
3. **トップレベルキー置換で畳む** — 読めたオブジェクトを列の順に畳む。後のオブジェクトが持つ
   **トップレベルキー**が前のものを置き換え、後のオブジェクトに無いトップキーは前の値がそのまま残る

**`multiple` でない config_file 要素はパス列長 1 の縮退形**であり、従来の挙動と一致する。単値と
`multiple` で別の規則を持たない。

#### 2.1 パスを供給しなければ列は空

config_file 要素のパスは cli > env > default のラダーで解決される (DR-050 §1)。どの席からも供給され
なければ読むべきファイルを指していないので、列は空になり config 席も空のままになる。**エラーではない**。

### 3. 畳むのはトップレベルキーまで — 深いマージはしない

fold はトップレベルのキー単位でのみ置換する。ネストした object の内側を再帰的に混ぜることはしない
(後のファイルのトップキーが object なら、その object 丸ごとで前を置き換える)。

**v1 にダイヤル語彙を持たない** (CFM-Q2-γ)。深いマージの需要は、合成済みのオブジェクトを返す
config_provider か、将来の別語彙が担う。深いマージを core に入れると「配列は連結か置換か」「欠損キーの
扱い」といったダイヤルを必ず呼び込み、語彙が増え続ける。

fold は値の中身を検査しない — キーに対応する値をそのまま置くだけである。JSON `null` の読み
(「供給なし」、DR-050 §4) は畳んだ後のオブジェクトを席が読む段の規則であって、fold の関心ではない。

### 4. committed Error と default 由来不在の黙認は、各パス独立に判定する

DR-050 §2 の分界は列の各パスにそれぞれ適用される (CFM-Q2-α):

- **committed なパスの読込失敗は Error** — 指定したのに読めないので、そのパスを供給した要素に帰属する
  Error になる
- **default 由来のパスの不在は黙認** — 設定ファイルはオプショナルという慣習どおり、そのパスは fold に
  寄与しないだけで列の残りは読まれ続ける

前のパスの committed 性が後のパスの判定に影響することはない。判定はパスごとに閉じている。

#### 4.1 committed 判定は link を透過する (CFL-Q1a)

**committed かどうかは、値を運んだ経路ではなく値の源席の cli / env 性で判定する。** link は config_file
セルを target にでき、CLI で明示した値が link 経由で config パスとして効く (実測 2026-08-12) が、この
パスも **committed として扱う** — 読めなければ Error になる。

committed の意味は「利用者が明示したのに読めないのは失敗」(DR-050 §2) であり、link は明示供給の
**搬送路**にすぎない。DR-031 は CLI と link を同順位の明示操作と規定しており、経路の違いで
「明示したかどうか」の判定が変わるのは規定と食い違う。

**観測面のタグは変わらない** — `sources` は経路を写す面なので、link 経由で確定した値の座のタグは
`link` のままである (DR-121 §4 は現役)。由来を辿るのは committed 判定 (内部) だけで、2 つは別軸である。

### 5. 排他選択と重ねの書き分け

- **重ねる** (下地を後段が部分的に上書き) — `multiple` の 1 要素。パス列が 2 本以上になる
- **どれか 1 つを選ぶ** — `multiple` を付けない 1 要素。値源ラダー (cli > env > default) が既に
  「どれか 1 つ」を担っており、選ばれた 1 本だけが列に入る

どちらも**要素は 1 つ**で、`multiple` の有無だけが違う。

### 6. 射程は同一スコープ内

本 DR が規定するのは、**あるスコープに宣言された** config_file 要素と、そのスコープの config 席の
関係である。異なるスコープ (root と子 command 等) に宣言された config_file の関係は確定しない
(「射程外」節)。

### 7. DR-050 §2 の分界の読み直し

DR-050 §2 の「複数ファイルのマージ戦略は provider の関心」は、**1 つのパス指定から provider が探索して
合成する類**を指す (CFM-Q2-β)。定義が**宣言した複数パス** (`multiple` の供給列) の fold は core の
席埋め規則であり、本 DR が正本である。両者は競合しない — provider は 1 パスから 1 オブジェクトを返す
契約のままで、その先の重ねを core が持つ。

### 8. 結果面での config_file 要素

config_file 要素自身は通常要素であり、露出キーを持てば確定したパスが `result` / `sources` に座る
(DR-135)。`multiple` なら**供給順のパス列** (`string[]`) がそのまま値になる — **読めたパスだけを残した列
ではない**。読めたかどうかは本 DR の fold の関心であって、要素の値を決めるのは要素自身のラダーである
(DR-050 §5 の依存順序が「値確定 → provider 読込」と段を分けている)。

## 根拠

### 並置に与える意味が無い

複数の config_file 要素を並べたときに何が起きるべきかを決めようとすると、どの案も 1 要素 `multiple` の
再発明になる (宣言順に連結する = multiple の供給順と同じ / どれか 1 つが勝つ = 1 要素のラダーと同じ)。
同じ意味を 2 通りの綴りで書けるようにすると、利用者は「どちらの書き方をしたか」で結果が変わらないことを
確認する手間を負う。**意味を与えられない構成は定義時に倒す**のが、語彙を 1 本に保つ最短経路である。

### 初版が並置を許した理由は 1 要素で満たされる

初版は「由来の違う設定ファイルを別々の入口 (long / env / default) で受け取る需要を定義側から締め出す」
ことを理由に definition-error 案 (CFM-Q1c) を退けた。この需要は**1 要素の中で満たされる** — 入口の
複数性は `alias` / long variant / env / default が担い、パスの複数性は `multiple` が担う。要素を分ける
必要があったのは、初版が「1 要素 = 1 パス」と読んでいたためである。

### 分ける理由が無い (単値と multiple)

「パス列 → 1 オブジェクト」の 1 規則で、単値も `multiple` も説明できる。単値は列長 1 の縮退形であり、
規則を 2 本持たない。

### provider 契約は無傷

fold は provider を N 回呼ぶだけで、1 パス → 1 オブジェクトの契約 (DR-050 §2) には触れていない。core が
持つのは「供給された順に畳む」という**宣言の読み方**であって、ファイルの探索や合成の知識ではない。

## 採用しなかった案

### 複数 config_file 要素の宣言順パス列連結 (初版 DR-133 の形)

そのスコープの全 config_file 要素を宣言順に走査して 1 本のパス列を作り、`multiple` の要素は自分の位置に
inline 展開する形。**CFM-Q3a (2026-08-14) で撤去**。並置の需要が実在しない (上記「初版が並置を許した
理由は 1 要素で満たされる」) 一方、同じ重ねが 2 通りの綴りで書けることになり、要素間の宣言順という
新しい観測軸を利用者に覚えさせていた。

### 並置は放置する — 検査せず挙動も未規定のまま (CFM-Q3b)

定義時に倒さない案。書けてしまう構成の挙動が未規定なら、実装ごとに違う結果が出て conformance が
割れる。意味を与えないと決めた以上、書けないようにするのが筋である。

### オブジェクト全体置換 — 最後にパスを持つ要素だけを読む (CFM-Q2 の (a))

勝った 1 パスだけを provider へ渡し、負けたパスは読まない形。**複数パスの動機である重ねが実現できない** —
後段のファイルに無いキーが前段から採られない。加えて負けたパスを読まないため、committed 指定したのに
読まれないパスが生まれ、「指定したのに読めないのは失敗」(DR-050 §2) の判定から静かに外れる。

### 先勝ち (CFM-Q1b)

先に供給されたパスが勝つ形。上書きの向きが設定レイヤの慣習と逆になる。fold の下では「先に来たものが
下地」という自然な読みがそのまま成り立つ。

### 深いマージ意味論 (CFM-Q1d)

§3 のとおりダイヤルを呼び込む。トップキー置換で止めるのは、規則を 1 文で言い切れる水準に保つため。

## 波及

### fixture

- `fixtures/definition-error/` に並置が `invalid-range` になる輪郭 (関与要素ごとに 1 件)
- `fixtures/value-sources/config/multi-file.json` / `multi-file-path-absent.json` — 2 要素並置の定義
  だったので、1 要素 `multiple` 形での fold pin へ組み替える
- `fixtures/value-sources/config/multi-file-multiple.json` — 3 要素並置だったので 1 要素 `multiple` +
  配列 `default` 形へ組み替える。トップキー置換 / 前段のみのキーの残存 / 各パス独立の判定 /
  DR-135 の結果面 pin (パス列が `string[]` として座る、読めなくても座る) をここに集約する
- 単一 config_file 要素の既存 fixture (`path` / `ladder` / `isomorphic-path` / `array-object` /
  `null-supply` / `value-typing`) は**列長 1 の縮退形として不変**

### docs 本体

- DESIGN §14.3 (config_file) の fold 規範と 1 スコープ 1 config_file
- REFERENCE §3.1 の `config_file` 行
- DR-050 §2 に分界の読み直し note (§7)

### 実装 (参照実装の乖離)

参照実装 (kuu.mbt) は「宣言順で最後にパスを持つ要素だけを読む全体置換」で動いており (実測 2026-08-12)、
`multiple` パス列の fold への追随が要る。`src/kuu/resolve.mbt` の `resolve_scope_config_with_export`
Phase 1/2 が単一の `cf_path` を上書きしながら provider を 1 回だけ呼ぶ形なので、パス列の構築と N 回読み・
fold へ作り替える必要がある。committed 性を要素間で持ち越す不具合 (§4 に反する) も同じ箇所にある。
並置の definition-error 検査 (§1) と committed の link 透過 (§4.1) は新規追加。

## 射程外

- **異なるスコープに宣言された config_file の関係** — root の config_file が子スコープの要素へ供給するか、
  子スコープ側の宣言が root を上書きするか。DR-050 §3 の同型対応 (`serve.port` ↔ config の `serve.port`) は
  root 宣言の config が木全体へ効く像を前提にしているが、参照実装はスコープごとに独立に解決しており
  root の config_file が子スコープの要素へ供給しない (実測 2026-08-12)。spec と参照実装の食い違いの解消を
  含めて別途扱う (`docs/issue/2026-08-12-nested-config-not-supplied.md`)
- **候補パスの探索** (「最初に読めた 1 個」) — §1.2 のとおり合成で書く方向、語彙の席は別 issue
- config ファイルの watch / 実行時再読込、プロファイル切替 (DR-050 の射程外のまま)
- 深いマージのダイヤル語彙 (§3)
