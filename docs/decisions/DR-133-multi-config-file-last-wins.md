# DR-133: 複数 config_file の後勝ち — 有効な config オブジェクトは 1 つ、粒度はオブジェクト全体

> 由来: kawaz 裁定 CFM-Q1a (2026-08-12、docs/QUESTIONS.md の CFM-Q1)。**DR-050 の射程外項
> 「複数の config_file 要素の合成 (システム設定 + ユーザ設定の 2 要素等) は本 DR では確定しない。
> canonical は単一の config_file 要素」の追認**であり、複数指定を合法として後勝ちを規範化する。
> 前提は DR-050 (config ファイル値源の正本) / DR-031 (値源ラダーの config 席) / DR-037 (Reject と
> Error の分界)。挙動の確認は参照実装 (kuu.mbt) への一時 fixture 投入による実測で行った。

## 決定

### 1. 同一スコープに複数の config_file 要素を宣言してよい

`type: "config_file"` の要素数に上限を置かない。複数宣言は definition-error にしない (CFM-Q1c 不採用)。
「システム設定 + ユーザ設定」のように、由来の違う設定ファイルを別々の要素 (別々の long / env / default) で
受け取る書き方が config レイヤの慣習として普通に要る。

### 2. 有効な config オブジェクトは 1 つ — 宣言順で最後に**パスを持つ**要素が決める

config 席 (DR-031 #3) を埋めるオブジェクトは、そのスコープでただ 1 つに定まる:

- 各 config_file 要素のパスは、従来どおり**要素ごとに独立な** cli > env > default のラダーで解決される (DR-050 §1)
- **cli / env / default のいずれからも供給されなかった要素は「パスを持たない」** — 読むべきファイルを
  指していないので後勝ちの主体になれず、一つ前の要素へ譲る
- パスを持つ要素のうち**宣言順で最後のもの**が勝ち、その要素のパスだけが config_provider に渡る

「最後の要素」ではなく「最後にパスを持つ要素」なのは、config_file 要素のパス自体が値源ラダーの住人だから
である。前者を採ると、`default` を持たない config_file 要素 (= 明示指定されたときだけ効く設定ファイル) が
宣言末尾にあるだけで、供給されていなくても先行要素を無効化してしまう。

### 3. 後勝ちの粒度は config オブジェクト**全体の置換**である

勝った要素のパスから読んだオブジェクトが config 席の唯一の供給源になる。**キー単位のレイヤ重ねではない**:

- 負けたファイルにしか無いキーは供給されない。その要素は自分の値源ラダーを下り、`default` に落ちる
  (source は `config` ではなく `default`)
- 勝ったパスが読めなければ config 席は空のままで、負けたファイルへフォールバックすることもない

キー単位で重ねる形 (深いマージを含む) は**複数ファイルのマージ戦略**であり、DR-050 §2 がそれを
**provider の関心**と規定している (「フォーマット (TOML / YAML / JSON)・探索ルール・複数ファイルの
マージ戦略は provider の関心」)。kuu core が席を埋める規則としてレイヤ重ねを持つと、この分界を core 側から
侵すことになる。重ねたい利用者は、重ねた結果を返す config_provider を書く (= 1 パス 1 オブジェクトの契約の
内側で解決する)。

### 4. 負けた要素のパスは読まれない — DR-050 §2 の Error / 黙認は勝った要素だけで判定する

provider が呼ばれるのは勝った 1 パスに対してのみである。負けた要素のパスは provider に渡らず、読込自体が
行われないので、そのパスが読めないものであっても失敗の判定対象にならない。したがって DR-050 §2 の

- committed なパス (cli / env 明示) の読込失敗は Error
- default 由来のパスの不在は黙認 (config 席が空になるだけ)

は、**勝った要素のパスの committed 性**だけで決まる。「先行要素が cli 明示だったから後続の default 由来
パスの不在も Error になる」といった持ち越しは無い (committed は勝ったパスの供給席の属性であって、
スコープに残る状態ではない)。

**参照実装の乖離 (追随が要る)**: kuu.mbt は committed フラグを config_file 要素間で持ち越しており、
「先行要素が cli / env 明示 + 勝った要素が default 由来で読めない」で本 DR に反する Error を出す
(実測 2026-08-12)。この形は resolve フェーズのエラーで args_pos を持たず failure schema に収まらない
(config/path.json の注記と同じ理由) ため fixture では pin できない。

### 5. 射程は同一スコープ内

本 DR が規定するのは、**同じスコープに宣言された** config_file 要素どうしの関係である。異なるスコープ
(root と子 command 等) に宣言された config_file の関係は確定しない (「射程外」節)。

## 根拠

### 後勝ちは config レイヤの慣習と一致する

設定ファイルを重ねる系 (シェルの rc、エディタ / ツールの system → user → project 階層) では、後から読んだ
ものが前を上書きする向きが支配的である。宣言順という定義上の順序をそのままレイヤ順として読ませるのが、
利用者にとって説明の要らない向きになる。

### 「1 席 1 オブジェクト」は provider 契約の帰結

config_provider の契約は `(path: string) → 階層オブジェクト | null` (DR-050 §2) であり、席を埋める素材は
1 パスにつき 1 オブジェクトである。複数の要素があっても席は 1 つなので、素材を選ぶか合成するかの二択に
なる。合成側は §3 のとおり provider の関心として既に分界済みなので、残る core の仕事は「どれを選ぶか」の
規則を決めることだけになる。

## 採用しなかった案

### 先勝ち (CFM-Q1b)

先に宣言した要素が勝つ形。上書きの向きが config レイヤの慣習と逆になるうえ、「後から足した設定ファイルの
宣言が効かない」という読みにくさが出る。

### 複数指定を definition-error にする (CFM-Q1c)

単一要素だけを合法とする形。由来の違う設定ファイルを別々の入口 (long / env / default) で受け取る需要を
定義側から締め出すことになる。単一に畳ませても、利用者は結局 provider 側やアプリ側で複数ファイルを扱う
ことになるので、締め出しの見返りが無い。

### マージ意味論を設計する (CFM-Q1d)

深いマージ等の合成規則を core に持つ形。DR-050 §2 が複数ファイルのマージ戦略を provider の関心として
分界済みで、そこを core 側から侵す。マージ規則は「配列は連結か置換か」「object の欠損キーの扱い」等の
ダイヤルを必ず呼び込むので、core が持てば語彙が増え続ける。

## 射程外

- **異なるスコープに宣言された config_file の関係** — root の config_file が子スコープの要素へ供給するか、
  子スコープ側の宣言が root を上書きするか。DR-050 §3 の同型対応 (`serve.port` ↔ config の `serve.port`) は
  root 宣言の config が木全体へ効く像を前提にしているが、参照実装はスコープごとに独立に解決しており
  root の config_file が子スコープの要素へ供給しない (実測 2026-08-12)。spec と参照実装の食い違いの解消を
  含めて別途扱う
- config ファイルの watch / 実行時再読込、プロファイル切替 (DR-050 の射程外のまま)
