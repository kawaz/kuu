## 1. 発題と問題意識

kawaz mid=1 の要旨:

- in/out に使う **型の葉は 5〜6 個だけ** (number / bool / string / map / list、+ null?)。
  これに tuple・構造化 type・それらの union が乗るが、葉の要素はそれだけ。
- 対して実際には、各オプション・ポジショナル・座には **各種 filter や parse 後の未知の T** が
  ぶら下がる。`number` を使うにも「string→number」では済まず、詳細な型指定・parse オプション・
  range 等の検証が要る。さらに ref / link / borrow でコピーや借用をした上で、コピー先に
  **追加の制限を足す**こともあり得る。
- 提案: 値を都度パースした生の型として扱うのをやめ、**入力値 (本質的には string で与えられる引数)・
  初期値・デフォルト値・制限などをカプセル化した、遅延評価されるオブジェクト**として持ち回る。
  都度パースを実際に行うかは実装の自由。**out の型としては基本 `string|number|bool|…` という
  型名の文字列だけで見て**、filter や link のチェーンをつなぐのがシンプル。
- ref した上で制限を加えた場合は、**ref 元のカプセルを内包し追加 filter を持つ新しいカプセル**になる
  イメージ。
- 解きたい問題: **色々な filter をどこでどういう順番で適用するかが、フラットな filter の累積として
  散らばり、全体として見るのが大変**。
- 定義上は各種 filter とセットでオプション定義されるが、それらを **AST からひっぺがしてカプセル化**し、
  表面上は最低限の type 文字列 (または map / list) までに見えるようにする。atomic になった時点では
  値に関わる詳細は見える必要が無いのでは。これで複雑さを減らせるのでは。registry の煩雑さも
  多少減らせるのでは。

統括の初期評価 (統括の推し、mid=1 への応答): 方向性に賛成。根拠は (1) 解こうとしている問題が
棚卸し §8 で実在確認済み (O-2 座席と装置の対応が 1対多/多対1/1対1 混在、O-3 accum 有無で属性名が
変わる、O-4 type→parser 対応と type 既定 filter chain が散文のみ、O-9 filterChain 二形 + 呼び出し
3 表記)、(2) runtime 側は既にセル・値源ラダー・遅延述語で「未確定の値の座 + 評価順」として
動いており、提案は**定義層 (wire/AST) の見え方を実行モデルに揃える**話と読めること。

## 2. 確定した設計性質 (kawaz 裁定済み)

以下は **確定**。以降の設計はこれを前提にする。

### 2.1 評価軸: 後方互換性とコストは考慮しない

> 後方互換性については無視して構いません。wire の書き換えコストもより良い設計の可能性の前では
> 一切気にしてはいけません。 (kawaz mid=4)

帰結: 案の優劣は **設計の良さ (問題意識の解消度・意味論の一貫性・将来の拡張余地) のみ**で決まる。
fixture 影響の見積りは移行の作業リストとして残すが、案の弱みには数えない。
「案 A は wire 互換」も利点に数えない。

### 2.2 C 案却下 — closure が型式に畳めない

案 C = 制約付き型 (refinement type) への畳み込み。`type:"number"` + `in_range:1:65535` を
「number & range(1,65535)」の型式に畳み、検証系 filter を型の一部・変換系だけをチェーンに残す案。

> C はないですね。ユーザ定義の closure によるチェックもスコープにいるので内部表現自体ができません。
> (kawaz mid=3)

### 2.3 B 案却下 — 実行時点は型から決まらない

案 B = `piece_filters` / `value_filters` / `final_filters` / `accum_filters` を廃し、
各段が自分の io を持つ単一 `pipeline: [...]` に統一し、**段の型接続**で静的検査する案。

> フィルタが複数の層に分かれているのは型の整合だけではなく、**必要な実行タイミングも全て異なる**
> ためです。pipeline にまとめるには無理がある。 (kawaz mid=5)

統括も同意 (mid=5 への応答)。具体例として: `in_range` (number→number) を「供給の都度」に掛けるか
「確定後 1 回」に掛けるかは**型が同一なので pipeline 内の型からは区別できない**。しかも
**観測が実際に違う** — 供給都度なら途中候補の reject (last-wins で後の供給が生きる余地、エラー帰属も
供給位置)、確定後なら最終値の reject。座席 4 種は「string 域 / T 域 / array 域」という型の層に加えて
**per-supply / post-settle / post-accumulate という実行時点の層**を名指ししており、後者は型に
還元できない。1 本化すると時点注釈付きの段が必要になり、それは座席の再発明。

この却下は後の検証でも裏づけられた (B' 報告 観点 2-b): 非 accum 要素では fan-in 点が存在しないため
`value_filters` と `final_filters` をチェーン位置で区別できず、B は **DR-102 §4 の observable な
argv_pos 差**を表現できない。DR-102 の「採用しなかった案」にある kawaz 裁定
「違うものを違うものとして扱え、同じにするな」とも衝突する。

### 2.4 補完は各位置で独立した 1 回の決定的実行

> 各カーソル位置での補完は現実的には内部で補完モードでのパースを個別に実行している筈で、
> プロセスとしては独立して閉じている。前の引数補完と今の位置での補完は関連しない。成功失敗の
> 判定となる別ブランチとして保持するといったことも不要 (というかそもそも別プロセスの話になるので
> 不可能というのが正しい)。それぞれの位置での補完は独立した 1 回の実行であり、`type:"file"` で
> exists とか readable とかのチェックがあるなら **IO 含めて必要なものは全て実行してよく**、
> 各補完結果は決定的なものになる。 (kawaz mid=2)

帰結: 遅延カプセルは補完時に単に強制評価されるだけで、**部分評価の特別機構は不要**。
「遅延性が補完を壊す」という初期の懸念は解消 (統括、mid=2 への応答)。

### 2.5 フェーズ別メモ化 = 実行内スナップショット一貫性

> 全てを遅延評価する必要はなく、各フェーズでの実行結果自体は内部にキャッシュしておいて、
> 実行済フェーズの再評価はスキップしてよい。例えば `type:file` で IO チェックまで済んでる
> オプション値は、別の枝でその値を見るときは既に IO チェックまで済んだ状態を持っているので、
> 枝の評価ごとに IO チェックするという無駄は抑制できる。 (kawaz mid=6)

統括の位置づけ (統括の推し、mid=6 への応答、kawaz からの異論なし): これは最適化を超えた**意味論**。
経路探索の複数枝が同じ (供給, 値) を評価するとき、IO チェックの結果が枝ごとに揺れたら
(評価の合間にファイルが消えた等) **経路探索自体が非決定になる**。「フェーズ結果は実行内で
キャッシュし再評価しない」を意味論に含めると、**1 回の実行はスナップショット的に決定的**が
構造から保証される。mid=2 の「各補完は独立した 1 回の決定的な実行」と同じ原理で貫ける。

### 2.6 メモ化の単位は「カプセルのインスタンス identity」

> uuid や高精度時間取得関数などはメモ化された時点で固定化されるのが正しい。もちろん ref で
> 構造だけコピーされて値自体は link していない別オプションの場合は別の値になるはず。
> `values:[{uuid},{uuid},{uuid}]` のような定義があったとしたら 3 つの値は別になる。
> `{type:"uuid",name:"uuid"}` があって `{.. values:[{link:"uuid"},{ref:"uuid"},{type:"uuid"}]}`
> のようなのがあったとしたら、3 つの tuple の最初の値は `name:"uuid"` と同じ値が入り、
> 他 2 つは別の値。 (kawaz mid=7)

この識別は既存の ref / link 意味論 (DESIGN §10.2/§10.3、DR-029 / DR-032 / DR-078) と一致する:

| 参照 | メモ化から見た意味 |
|---|---|
| `link` | **インスタンス共有** — 同じカプセルインスタンスを指すので、評価結果 (メモ化済みフェーズ) ごと共有 |
| `ref` | **プランの複製** — 構造 (評価計画) だけ複製した新インスタンス。独立に評価され別値 |
| inline 定義 | **新インスタンス** — 同上 |

帰結 (統括の推し、mid=7 への応答): 非決定 fn の規則は「1 実行 1 値」ではなく
**「1 実行 1 インスタンス 1 値」**。さらに、装置が宣言すべきは「メモ化可否」ではなく
**「再評価したら同じ値が出るか」** (deterministic / per-evaluation) であり、メモ化は決定性に
関わらず常に効く (インスタンスの評価は 1 回だけ、が一様規則)。決定性の宣言は lint や説明
(「この値は実行ごとに変わる」) にだけ効き、**評価意味論は決定性で場合分けしなくて済む**。

### 2.7 カプセルは「名前付き純データ」— closure は持たない

**発題の「遅延評価オブジェクト」という語は、既存の closure 禁則と字面で衝突する** (A 報告 材料 7):

> `docs/PIPELINE.md` L148 (由来 DR-010): **AST にはクロージャを持たせない** — フィールド名と
> 呼び出し席で registry が決まり、wire には名前 + args だけが載る

同線の規範: DR-042「再解釈 matcher は名前付きデータ」、DR-110 §3-4「opaque は『直列化不能』を
意味しない」。matcher が先例なので実現可能だが、**カプセルは「名前付き純データ (宣言)」と定義し、
遅延評価・メモ化は evaluator 側の実装として言葉を分ける**必要がある。以降の worker 指示・DR 起草で
語彙に注意する (A 報告が「この語のまま worker に渡すと closure 実装に流れる」と警告)。

関連する禁則がもう 1 つ (A 報告 材料 7): **カプセルに descriptor を与えてはいけない** —
DR-107 §1「descriptor 体系は宣言される registry 住人を対象とし、評価器内部の実装装置は対象外」。
matcher を role に載せなかったのと同じ線。

### 2.8 供給の解決は要素に閉じない (3 層ある)

A 報告 材料 3 が実在の規則 3 つを挙げる。カプセルを要素単位だけで設計すると壁に当たる:

| 層 | 規則 | 出典 |
|---|---|---|
| **スコープ層** | config パス列は「そのスコープの config_file 要素を宣言順に走査」して fold。`committed` はパスごとの属性 | DR-133 §1 / §3 |
| **要素横断 DAG** | `default_fn` の `observes` 依存グラフの位相順 | DR-114 §10 / DR-087 / DR-088 |
| **射影後の層** | default 充填判定は「export_key 適用後の**結果 cell** 単位」 | DR-031 UX-Q7R 追記 / DR-120 |

A 報告はこれを根拠に「供給側はカプセルに入れるな」と結論した。統括の裁定案は §4.5 で分岐を
整理する (宣言と解決を分ければ両立する、というのが統括の推し)。

## 3. B' 案の現在形 — 時点構造つき値カプセル

### 3.1 骨格

案 B (pipeline 1 本化) の却下を受けた方向修正。「1 本チェーン」ではなく
**「時点構造を持つ 1 個の値カプセル」を wire の第一級にする** (統括、mid=5 への応答で提示)。
B' 報告の補正 (観点 2-a) を反映した現在形:

```jsonc
{"name": "port", "long": true,
 "<カプセル名は未裁定>": {
   "piece":     [...],      // string → string   (parse より前、piece 単位)
   "type":      "number",   // 境界マーカー: string → T
   "each":      [...],      // T → T             (parse より後、piece 単位)
   "settled":   [...],      // T → T             (確定後 1 回、非 accum)
   "collected": [...]       // Acc → Acc         (累積後)
 }}
```

性格づけ (mid=1〜7 + 両報告を反映した統括の整理):

- **構造**: 時点 field を持つ 1 オブジェクト。`type` が string 域 → T 域の境界
- **評価**: インスタンス単位のフェーズ別メモ化つき遅延評価。実行内スナップショット一貫性が意味論 (§2.5/§2.6)
- **合成**: `ref` = プラン複製 + field 単位の追記。`link` = インスタンス共有、`borrow` = default 席の fn (§3.5)
- **正体**: 名前付き純データ。評価器ではない (§2.7)

### 3.2 立脚点 — 新提案ではなく DR-034 の未実現部分 (両報告が独立に到達)

**B' 報告と A 報告が独立に同じ一次アンカーに到達した**のが本検証の最大の収穫。
`docs/decisions/DR-034-multiple-structure.md` §「type と multiple は同じ属性平面への参照」
(現役、Superseded 節に無い。起草時に再確認済み) が既に値カプセルを概念として持っている:

> 属性平面 (全属性): processor / default / accumulator / separator / collector / 入力消費数 / …
> type が主に指す断面: processor, default, 入力消費数
> multiple が主に指す断面: accumulator, collector, separator
> 合成順: 1. 組み込み初期値 → 2. type プリセット → 3. multiple プリセット → 4. node 直書き (後ろほど優先)

つまり **kuu は既に「値カプセル」を持っていて、wire がそれをフラットに展開していただけ**
(B' 報告 §立脚点)。`type` も `multiple` も同一平面の異なる断面への参照であって、要素直下に並ぶ
フラットな兄弟属性ではない。加えて DR-028 §「type は参照糖衣」が `type:"color"` を
「definitions の**構造テンプレ**への参照」と規定済みで、type がカプセル丸ごとのプリセットを指すのは
既定路線の内側。同じ発見を A 報告も観点 1 の筆頭 (「一次アンカー」、DESIGN §3.5 L312-324 併記) に置いた。

> B は新しい統合軸の発明だったが、B' は既存 DR の未実現部分の実装。正当化の強さが違う。
> (B' 報告)

### 3.3 field 粒度 — 最低 5 個 (統括の 3 field 素描は破綻)

統括の初期素描 `{type, each, settled, collected}` は **`each` が string 域と T 域を統合していた**
ため破綻する (B' 報告 観点 2-a、A 報告 材料 1 も同旨)。DR-050 §4 の通過段差はまさにその 2 つの
**間**を通る:

- config JSON string → `piece_filters` → parse → `value_filters`
- config の型一致な非 string (number/bool) / tty 観測 bool / cell fn が返す型付き Value →
  **`piece_filters` と parse をスキップ**して `value_filters` のみ

`each` に統合すると「each の途中まではスキップ」が言えない。**string 域と T 域は同じ per-piece
時点だが parse を挟んで型が違うので、別 field でなければならない。**

`type` をカプセル内の**境界マーカー**に置くと、DR-050 §4 が
「**供給値が string ならカプセル先頭から、要素型 T と一致するなら `type` field の直後から入る**」
の 1 行で書ける。現行の「型の帰結」という説明が**カプセル内の位置関係として構造的に可視になる** —
フラット wire では piece_filters と value_filters の間に parse が挟まることが見た目から読めない
(属性順序に意味がないため)。B' 報告はここを「現行に対する明確な改善」と評価。

`settled` / `collected` の分離も必須 (B' 報告 観点 2-e-1): accum 排他 (DR-102 §3) があるため。
「`collected` 1 個にまとめて入力型は accum 有無で T か T[] か変わる」という誘惑は、DR-102 が
「違うものを同じものとして扱わない」で棄却した形そのもの (1 属性に 2 型を内包)。

**結果: 現行 4 座席 + type がそのまま 5 field になる。**

### 3.4 `multiple` 束ね名の解体 (B' 固有の最大の収穫)

現行 `multiple: {accumulator, collector, separator, flatten}` の 4 者は**時点の異なる別々の装置**が
1 束ね名に同居している (B' 報告 観点 2-e-2):

| 装置 | 時点 | カプセル内の座 |
|---|---|---|
| `separator` | 分割時点 | `piece` field の手前 |
| `accumulator` | 累積時点 | `each` と `collected` の間 |
| `collector` | 最終整形 | `collected` の後 |
| `flatten` | accumulator の引数 (DR-111 §4 のまま) | accumulator に従属 |

**時点順に並べたカプセルに配置すると `multiple` という束ね名の存在理由が消える** —
「複数値経路のスイッチ」の意味は「これらの field が書かれていること」に還元される。
これは棚卸し **O-2 (座席と装置の対応が 1対多/多対1/1対1 の混在) と O-6 (collector 段が
PIPELINE 7 段図に現れない) を同時に解消する**。

副産物: `is_accum_elem` 判定 (現行は `multiple`/`repeat`/`separator` のいずれか) が
カプセル内 field の存在で決まり、**判定が局所化する**。
DR-036 の multiple registry プリセット (`"append"` = accumulator + collector + separator のセット) は
「カプセル断片プリセット」として DR-034 §合成順の 3 段目に自然に座り、DR-036 の糖衣構造は無傷。

### 3.5 「空 []」と「不成立 ⊘」を区別する

非 accum 要素にとって `accum_filters` 席は「空」ではなく**構造上不成立**
(A 報告 材料 2 / B' 報告も同旨、出典 DR-102 §1/§3: accum 適格性 = `multiple`/`repeat`/`separator` の
いずれか = `is_accum_elem`、誤った側への宣言は definition-error `invalid-range`)。
カプセルが全 field を一様に持って両者を `[]` に潰すと、**wrong-seat の definition-error が
構造から導出できなくなる**。カプセルの型でこの 2 状態を区別する必要がある。

### 3.6 時点は静的骨格ではない — 「値源 × 型」で決まる動的経路

A 報告 材料 1 が最重要として挙げた点。**どの段を通るかは値源の種別ではなく値の JSON 型が決める**
(DR-050 §4 の一般規則、DR-102 §5 が非 accum 要素の宣言 default へも適用範囲を拡張):

| 入力 | string 域 | parse | T 域 | 累積 | 出典 (A 報告による) |
|---|---|---|---|---|---|
| CLI args | 通る | 通る | 通る | 通る | PIPELINE §2 |
| env (常に string) | 通る | 通る | 通る | separator 分割も効く | DR-049 §2 |
| config: JSON string | 通る | 通る | 通る | 通る | DR-050 §4 |
| config: 型一致の非 string | **スキップ** | **スキップ** | 通る | — | DR-050 §4 (型の帰結であって特別規則ではない) |
| config / 宣言 default の array | piece が string なら通る | 同左 | 各 piece に | **分割済み pieces** として accumulator へ | DR-050 §4 / DR-083 §2 |
| tty 観測値 (native bool) | スキップ | スキップ | 通る | — | DESIGN §12b |
| 宣言 default: JSON string | 通る | 通る | 通る | 通る | DR-102 §5 |
| cell fn が返す型付き `Value` | **再通過しない** | **再通過しない** | 通る (通常の set operand) | 通る | DR-114 §6.1 |
| cell fn が返す `null` Value | — | — | **dispatcher が filter を呼ばず素通し** | — | DR-131 §1.1 |
| `Sentinel` (`default`/`empty`) | — | — | 対象 piece が生じない | — | DESIGN §8.3 / DR-130 §3 |

**含意**: 時点構造を静的に持たせても実行時の型ディスパッチは残る。時点 field は
「静的な通過経路」ではなく **「この段に来た値に適用するものの宣言」**であり、
どの段から入るかは値の型が決める。`type` を境界マーカーにする案 (§3.3) はこの動的性と整合する
(統括の推し、mid=8 直後の補足として kawaz にも伝達済み)。

**残る穴** (B' 報告 観点 2-a): DR-050 §4 の寛容 coercion (string 要素に JSON `1.5` が来たら
`"1.5"` 化して head から入る) は型一致判定から導けず、別規則として残る。B でも B' でも解消しない。

### 3.7 reject の argv_pos 帰属は field 名で決まる (B の致命傷が起きない)

field 名が時点を保つので、DR-102 §4 + M-7 明確化の 3 行がそのまま field 規定になる
(B' 報告 観点 2-b):

- `piece` → piece 実位置がある場合はそこ (入力源を問わない)
- `each` → CLI 由来は piece 実位置、非 CLI 由来は `argv.length`
- `settled` / `collected` → 常に `argv.length`

### 4.3 DR-062 の継承機構は実地ゼロ (A 報告の追加実測)

`fixtures/` + `corpus/` 全 JSON の構造走査:

| 対象 | 出現 |
|---|---|
| filter chain の object 二形 `{prepend, append}` (DR-062 §2 / DESIGN §8.5) | **0 件** |
| `definitions.types` に filter chain を持つ定義 (継承元 #2「type registry のデフォルト」) | **0 件** |
| `ref` と `*_filters` を同時に持つ fixture (継承元 #1「ref 元のそのフィールド」) | **0 件** |

**3 経路すべて実地ゼロ**。合成を再設計する際、この領域の裁定は散文規範だけを根拠に行うことになる。
逆に言えば**既存 golden との衝突が原理的に起きない領域**でもある (A 報告)。

なお A 報告は、現規範の合成が **二層構造**であることを強調する:

```
1. ref 元の「宣言フィールド」を継承                          (DESIGN §10.1)
2. 参照側の宣言でフィールド単位に丸ごと上書き (累積しない)      (DR-062 §4)
3. 合成後の宣言から chain を 1 回だけ解決
     継承元解決順: ref 元 → type registry のデフォルト → 空配列  (DR-062 §3)
4. 二形 {prepend, append} をこの解決の最終段で合成
     合成順: prepend ++ 継承 chain ++ append、中間挿入は表現しない (DESIGN §8.5 / DR-062 §5)
```

chain の中身は `{prepend, append}` という**明示的に宣言された演算子**を通じてのみ累積し、
その宣言フィールド自体は ref 越しに丸ごと上書きされる。カプセルを**入れ子で暗黙累積**させると
(a) DR-062 §1 が `@base` sentinel を退けた理由 (「型面から存在が見えない」= 発見不能性) が
そのまま当たり、(b) §5 が意図的に排除した**中間挿入が構造的に可能**になる。

A 報告は付言として、DR-062 §5 の理由づけ (「実需が出るまで公理を増やさない」) は
「corpus 不在を表現力削減の論拠にしない」に照らすと単独では弱く、
「継承 chain の内部構造への依存を生み type 側の変更が利用側を壊す結合になる」(§採用しなかった案)
という構造的理由の方が本体である、と指摘した。**属性平面を再設計する際に改めて問い直す価値のある論点。**

### 4.4 命名軸の混在 — カプセル化と分離すべき (B' 報告 最重要の提言)

DR-079 §2 の裁定理由は「pre は parse 基準・post は accumulator 基準という**別の軸を指す名前が
対に見える**非対称が誤読を構造的に誘発した」こと。時点軸で一貫させる限り DR-079 が排除した欠陥
そのものは再来しないので、時点軸への変更は正当化可能。**問題は統括の素描が軸を混ぜていること**:

| field | 何の軸か |
|---|---|
| `each` | 適用**単位** (per-piece) |
| `settled` | 値の**様態** (確定済み) |
| `collected` | 値の**様態** (累積済み) |
| `piece` (追加必須) | 作用**対象** |

**4 語が 3 つの異なる軸から来ている** — DR-079 §2 が解消した非対称の、より悪い版になりかねない。

> 提言: **カプセル化 (構造の改善) と命名軸の変更 (DR-079 §2 の再裁定) を 2 つの裁定に分ける。**
> カプセル化は DR-034 の属性平面の実現として単独で正当化でき、**現行の作用対象アンカー名を
> そのまま field 名にすれば軸は一貫する** (`piece`/`value`/`final`/`accum` — `_filters` 接尾辞は
> カプセル内では冗長なので落とせる)。時点名を望むなら全 field を単一軸で名付けきる案を別途起こす。
> 混在した状態で同時に決めると、どちらの是非も評価できなくなる。 (B' 報告 観点 2-e-3)

### 4.5 供給席をカプセルに入れるか — 両報告が対立、統括に裁定案あり

**B' 報告 (入れる推し、観点 2-e-4)**:
- DR-034 の属性平面が `default` を明示的に type の断面に含めている
- 発題の「値の詳細が散らばる」に env / config_key / default も含まれる。「カプセル化した遅延評価
  オブジェクト」は**供給から確定までの全部**を含意する (kawaz mid=1)
- 実測: ノード属性 57 個中、値関連は 13 個前後 (`type` `piece_filters` `value_filters`
  `final_filters` `accum_filters` `multiple` `default` `default_fn` `env` `config_key`
  `completer` `value` `value_name`)。カプセルに入れれば要素直下は構造・名前・表示メタだけになり、
  **要素の読み方が「構造属性 + 値カプセル」の 2 分に整理される**

**A 報告 (入れるな、材料 3・6)**: 値源の解決が**実際に要素単位に閉じていない** (§2.8 の 3 層)。
要素単位のカプセルに入らないものを入れると、外にスコープ層と結果 cell 層が必要になり
**層が 1 つ減るどころか 3 層に増える**。DR-110 §6 #10/#11 (結果セル構築と席テーブルは engine)
および同 DR が opaque 化案を却下した理由 (L319-325) はこの構造的事実の言い換え。

**統括の裁定案 (未裁定、統括の推し)**: **「宣言の置き場」と「解決の局所性」を分ければ両立する。**
現行 wire でも `env:` / `default` は要素の属性として書かれ、解決は横断機構 (席テーブル) が担っている。
カプセル化は**宣言の置き場を 1 段深くするだけ**で、解決機構 (engine、DR-110 PKG-Q2=a) は変えない。
A 報告の「3 層に増える」は**カプセルが解決まで内包すると読んだ場合の帰結**で、宣言純データに
限定すれば発生しない。→ **宣言としては入れる、解決はカプセルの外**。

### 4.6 ref 合成 — 両報告は衝突していない (統括の判定)

A 報告は「カプセル内包の暗黙累積は DR-062 の二層構造より劣る (発見不能性・中間挿入の穴)」と批判した
(§4.3)。統括の判定 (統括の推し): **これは案 A の合成様式への批判であって B' には当たらない**。
B' の合成案 (c-1) は「**カプセル内 field 単位で DR-062 の流儀 (後勝ち + 明示 `{prepend, append}`) を
そのまま適用**」であり、暗黙累積ではない。

B' 報告 観点 2-c の整理: 合成順は DR-034 の 4 段がそのままカプセル合成になる
(組み込み → type プリセットのカプセル → multiple プリセットのカプセル断片 → 要素直書き →
ref 継承 (DR-062 §4 後勝ち))。**field 単位で `{prepend, append}` が効くので、B が壊した
中間挿入問題 (「parse の後・累積の前に足したい」が書けない) は発生せず、DR-062 §5 を覆さずに済む。**

代表例 — ref + 追加 filter (B' 報告 追加の問い):

```jsonc
{"ref": "base_port",
 "<capsule>": {"each": {"append": ["in_range:1024:65535"]}}}
```

**field 単位の合成なので `type` と `piece` を ref 元から継承したまま `each` だけに足せる。**
B ではここが表現不能だった (両端にしか足せない)。B' の優位が最も鮮明に出る例。

### 4.7 link / borrow はカプセル合成ではない

A 報告 材料 4 (出典 DESIGN §10.3 / DR-032)。**合成が起きるのは `ref` だけ**:

| 参照 | 指すもの | カプセル合成 |
|---|---|---|
| `ref: Y` | name (ノード) の**構造継承** | 起きうる (向きは §4.3) |
| `link: Z` | name (値セル) への**値同期**、1 実体 : N 参照 (DESIGN §10.2 / DR-029) | **起きない** — 参照側は自分のカプセルを持たず実体のセルへ効果を送るだけ |
| `borrow:<source>` | default 席の **cell fn** (DR-125 §3) | **起きない** — 構造継承でなく、default 席の fn が実行時に他セルを引く |

`borrow` は DR-125 が `inherit` 席を廃止して**ラダーの席でなく fn 呼び出しに寄せた**判断
(ラダーは 4 段に縮小)。カプセル合成として括り直すと DR-125 を逆行させる。
これは §2.6 の kawaz 裁定 (link = インスタンス共有 / ref = 複製) と整合する。

### 4.8 カプセル名 — `value` は使えない (ただし吸収の機会)

`value` は既に wire 属性として実在 (`schema/wire.schema.json` の `node.properties.value`、
REFERENCE §2.1「実体だけノード」、DESIGN §5.2「消費 0 の宣言定数 (`const`、DR-031)」。
起草時に DESIGN.md L404/L408/L891 で再確認済み)。`values` も or のショートハンド糖衣 (DESIGN §5.3)。

**ただし衝突ではなく吸収の機会** (B' 報告 観点 2-e-5): `value:` の const はカプセルの一 field
(`const`) として自然に座る — セル初期化位相の宣言定数はまさに「その値がどう作られるか」の一部。
`value` を空けてカプセル名に転用できる。

`cell` は不可 (DR-102 で kawaz が「cell という名前自体が『値の置き場』という内部事情由来で
利用者の目的に合っていない」と明示棄却)。省略形も不可。**カプセル名は裁定事項。**

| **registry 区分・`domain` 軸は現状維持** | lane が保たれるので filters (3 lane) / cell_fns / types / accumulators の 4 区分はそのまま。B の収穫 (12 名を「チェーン段装置」1 区分に畳む、`domain` 軸削除) は得られない | 両報告 |

| **棚卸し D-1 は別作業** | `unset` の出力型が descriptor/schema と DR-131/DR-114/PIPELINE/REFERENCE で食い違う件は正本間ドリフト。カプセル化では解けない | A 報告 問い 1 |

### 4.10 案 A の判定 (参考)

**単独では不採用** (A 報告 自身の総合所見):

> 最大の弱みは「wire 不変」という前提そのもの。発題の「全体把握が大変」を経験するのは wire を
> 読み書きする人であり、wire を据え置く案 A は構造上その問題を解けない。さらに案 A は自己矛盾を
> 抱える — 属性平面はドメインモデルであり wire もカプセルもその射影なので、**属性平面を第一級に
> すれば wire 表面を据え置く理由は互換性しか残らず、その理由は今回の裁定 (mid=4) で消えた**。

観測不変性そのものは実測で成立する (§4.2) が、それは案の価値にならない。
A 報告の材料は B' の内部モデル設計にそのまま流用され、本ノートの §2.7 / §2.8 / §3.5 / §3.6 /
§4.3 / §4.7 がそれに当たる。

## 5. 未裁定の分岐 (次に決めるもの)

### 5.1 進行順序 (両報告の提言 + 統括の推し)

A 報告の提言する順序を統括も採用:

1. **属性平面 (DR-034) を確定させる** — どの field が存在し、何が何をどの順で合成し、
   「空 []」と「不成立 ⊘」をどう区別し (§3.5)、時点が入力型でどう分岐するか (§3.6)。
   **wire もカプセルもその射影なので最初に決める**
2. **wire 射影を属性平面から再設計するかを判断する** — 現在の 4 座席 + 二形が良い射影かを
   互換性抜きで問い直す。DR-102 の「違うものを違うものとして扱え」は座席分割の根拠として今も
   生きるが、それが **4 という数**を要求しているかは別問題
3. **カプセルを (1) の実体化として導く**

### 5.2 裁定待ちの分岐 (依存順、B' 報告 §先に決めるべき順序 に準拠)

| # | 分岐 | 選択肢 | 現在の推し |
|---|---|---|---|
| **①** | **カプセルの射程** | (a) 変換 field だけ (type + filter 4 座席) / (b) 供給席・completer・value_name も含む | **(b)** — B' 報告・統括とも。ただし A 報告は「解決まで含めるなら不可」と留保。統括裁定案は「**宣言は入れる / 解決は外**」(§4.5)。**ここで B' の価値の大半が決まる** — (a) なら「4 属性を 1 段入れ子にしただけ」で利得が小さい |
| **②** | **field の粒度** | 最低 5 個 (`piece`/`type`/`each`/`settled`/`collected`) + accumulator/separator/collector の座。`multiple` 束ね名を廃するか | 5 field 必須は確定的 (§3.3)。`multiple` 解体は B' 固有の最大の収穫 (§3.4) |

| **⑤** | **合成粒度** | (c-1) カプセル内 field 単位で後勝ち (DR-034 §合成順 / DR-062 §4 の流儀) / (c-2) カプセル丸ごと後勝ち (DR-133 §2 の流儀) | **(c-1)** (B' 報告・統括)。理由は表現力でなく責務 — DR-133 の「深いマージはしない」は *config ファイルの値* の話で、「配列は連結か置換か」のダイヤルを呼び込むことが忌避理由。カプセルの field は値でなく**宣言の構成要素**で、field ごとの合成規則が既に型で決まっている。ただし **「深さ 1 段のマージだけ許す」線を明示する DR が要る** — 引かないと DR-133 §2 との一貫性を問われる |

①と②が決まれば③と④は独立に処理できる (B' 報告)。

### 5.3 派生論点 — 構造化された type の定義形 (kawaz mid=8、未着手)

議論の途中で kawaz が次の論点を提示した (mid=8)。**本ノート起草時点で未分析**:

> 現時点で構造化された type についても検討しましょう。例えば何度か例に使った
> `color` は `(in:[int,int,int] -> out:[int,int,int]) | (in:string -> out:string)` の union です。
>
> `timerange` は
> ```
> (in:string                -> out:{since:timestamp?, until:timestamp?})
> | (in:[string,string]     -> out:{since:timestamp,  until:timestamp})
> | (in:{since:string}      -> out:{since:timestamp?, until:timestamp?})   // {type:timestamp, link:"timerange.since"} みたいなので部分注入マージされるパターン？
> | (in:{until:string}      -> out:{since:timestamp?, until:timestamp?})
> ```
> とかいうのが出てくるはずです。これをどう定義されるべきかなど

観点として効きそうな既存規範 (未検証、次セッションで裏取りが要る): DR-028 (type = 構造テンプレへの
参照糖衣)、DR-128 (`input_structure` splice、value_parser は Value を受ける)、
DR-126 / DR-132 / DR-074 / DR-075 / DR-076 (型系)、`docs/research/2026-08-02-record-builtin-type-design.md`。
カプセル設計との関係では「**in の形ごとに違う経路を持つ type** をカプセルの `type` field
(境界マーカー、§3.3) がどう表現するか」が接点になる。
